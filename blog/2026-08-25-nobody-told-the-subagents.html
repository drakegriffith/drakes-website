Nobody Told The Subagents

August 25, 2026

Every terminal I open gets handed a stack of house rules before I type anything. Never trust a number without the command that produced it. A check that inspected zero things failed, it did not pass. Keep a control, something you already know the answer to, so you can tell "found nothing" from "never looked." I have been paying about a third of my context window for that stack for weeks and I consider it money well spent.

This morning I wondered whether the helpers get the same stack. When my terminal farms a job out to a subagent, does that subagent see the rules, or does it start empty?

It starts empty.

The stack arrives through a startup hook, and that hook fires on four events: a session starting, resuming, clearing, or compacting. Spawning a helper is none of the four. I ran four probes with the tools switched off, so nothing could be read off disk and mistaken for something that was already in the window. All four came back the same. Nothing.

That was the part I expected. Here is the part I did not.

There is a second channel, the memory file, and whether it reaches a helper depends on which kind of helper you asked for. The general-purpose one gets it. The two read-only ones, the ones named Explore and Plan, get nothing at all.

My router had been pointing every research job at Explore for weeks.

So every time I said "go look at this and report back," the thing I sent had full tool access, could run any command it liked, and had never been told that a sweep which inspected zero files is a failure rather than a pass. It was allowed to do everything and had been told nothing. I fixed that in about twenty minutes by writing my own read-only helper, three hundred tokens, carrying the four rules in its own instructions instead of pointing at a file it cannot see.

Then, because I was already in there, I asked whether any other helper was worth adding.

I did not want to answer that by guessing, because guessing is how you end up with twenty-seven agents named things like refactor-buddy. So I sent eight of them out to dig, and I deliberately did not tell any of them what I was hoping to find. If you hand a searcher your vocabulary, it finds your vocabulary.

They came back with two months of commits, 5,605 of them across 26 repos, a thousand and eighty issues across 17, and every job I had handed off in the last two days. Two shapes showed up over and over.

The first was checking. Eleven times I had typed out, by hand, some version of "attack this, do not bless it, re-derive every claim yourself, the producer's own evidence does not count." Eleven times, from scratch, slightly different each time. And in the issue tracker, the single most common recurring failure across four different repos was thirty-six tickets that all say the same thing in different words: something reported a pass over work it never actually looked at.

Eleven hand-written briefs, and thirty-six tickets about the exact failure those briefs exist to catch. That is not a hunch, that is a job description.

The second was sizing. Twelve times something had gone out to read a ticket and report back how hard it was and what files it would touch. Nine of those twelve went to Explore. The one that gets no rules.

So I built two: one that checks, one that sizes. Both hold exactly the same tools as the researcher I built this morning, which was the useful surprise. I went in thinking the answer was permissions, some agent that is allowed less. It is not. What makes them different is what they were told and what they are forbidden to have already seen. A checker that read the worker's notes first is not a checker.

Then I wrote a little script to install them on both my machines, and it deleted them.

One of my four config folders is a symlink pointing back at the folder the script was installing from. The script compared the names of the paths, saw two different names, and treated the source as a destination. It backed up the thing it was installing, deleted it, and left a link pointing at itself. Nothing was actually lost, because I had made it back up before deleting, which is the only reason this is a funny story instead of a different kind of story.

The lesson is that a path can be a nickname. Two different names can be the same place, and my dry run could not see it because I taught it to read the label instead of following the road.

Meanwhile the helpers kept catching me.

One of them reported that a directory holds fifty items. It holds forty-eight. It had read that number off a listing that prints the current folder and the parent folder as two of the rows. In the same message it gave me a count of thirty-two that was exactly right, and the only difference between the two numbers is that the correct one came with the command that produced it and the wrong one did not. That is the rule I make them carry, catching the thing carrying it.

Then I told everyone there had been sixty-one jobs dispatched. There had been sixty-four. My search could not see two jobs sharing a single line of the log. A subagent told me I was wrong and it was right, which I am recording here because I said it out loud earlier with some confidence.

And I asked the new checker to confirm it had loaded properly, while forbidding it from reading any files. It confirmed what it could and then marked its own answer as unverifiable, on the grounds that it had only my word for it. Correct. Annoying. Correct.

The last thing was getting all this onto the laptop. I have Tailscale, so this should have been thirty seconds. Tailscale found the laptop instantly, direct connection, no complaints. Port 22 refused. I tried Tailscale's own ssh command, which turned out to be a wrapper around the regular ssh command, so it refused in precisely the same way, just with more branding.

So I stopped trying to reach across, and put the install step inside the sync job that already runs on both machines every fifteen minutes. Now each machine installs itself from a file it was already downloading, and nothing has to accept a connection from anything. This is better than what I originally asked for, which happens more often than I would like to admit.

Last thing I did was count. Not to prove anything, to have a starting line. Right now, before any of this had a chance to matter, thirteen checking-shaped jobs and thirty scoping-shaped jobs went to the generic helper instead of the ones I just built. Those are all from before the seats existed, so they are the baseline, not the failure.

In a week I run the same count again. If those numbers stay flat and the new names show up instead, the two seats earned their place. If the old numbers keep climbing, then I built two things nobody uses, and the honest move is to delete them and say so here.

I wrote the counting script down and committed it, so that when the week is up I cannot quietly decide not to look.
